작성: 2026-08-19. 대상: ① 구 ECS의 PLC 기록 DLL(질문 1~5) ② 첨부 `260818_ECS-분석-PLC사양및시나리오_LG생명과학_V1.1.ppt`(PLC담당자 조사, SC_2~SC_5 반송 시나리오) 전수 대조(질문 6).
관련 문서: [legacy_ecs_plc_writes.md](legacy_ecs_plc_writes.md) (태그 대입 5단계·주소 계산 3단계)

## 1. 질문 1~4: DLL과 기록 경로

**Q1/Q2. DLL로 기록하는가? 소스는 있는가?** → 예/예.
구 ECS(HECS.exe)는 ezMCS 프레임워크(**ECP.dll**)의 태그(Observable) 대입으로 기록하며, 그 DLL 소스가 리포에 있다:
`Backup/ECP/Com/FieldBus/Fenet/` — `FenetDriver.cs`(2,397줄), `FenetConnection.cs`, `FenetMemory.cs`, `FenetCommand.cs`(미사용 데이터클래스).

**Q3. ECS→DB→DLL 순으로 기록하는가?** → **아니다.** DB(TB_OBSERVABLE/TB_FIELDBUSDRIVER)는 **기동 시 매핑(태그명→주소)을 로드하는 정의 저장소**일 뿐, 매 기록이 DB를 거치지 않는다. 실제 기록은 ECS 프로세스 안에서:
`태그 대입 → ECP.dll(FenetDriver) → TCP 소켓(FEnet 프레임) → PLC` 직송.

**Q4. 어디(어떤 함수)에서 기록하는가?** 쓰기 체인(파일:줄):

| 단계 | 함수 | 위치 |
|---|---|---|
| ① 태그 대입 | `Observable.Value` setter → `SetObservableValue` | Observable.cs:406, 964 |
| ② 동기 쓰기 | `WriteValueSync` → `Driver.Write(this, value)` | Observable.cs:478, 515 |
| ③ 드라이버 진입 | `FenetDriver.Write(Observable, object)` | FenetDriver.cs:**2067** |
| ④ 타입 분기 | BOOLEAN→`WriteBit`(1106) / SHORT→`WriteWord`(1567/1669) / STRING→`WriteWordA`(1831) | FenetDriver.cs |
| ⑤ 프레임 조립 | `mdSend`(607) 또는 비트 전용 `mdDevSet`(533)/`mdDevRst`(459) | FenetDriver.cs |
| ⑥ 송신 | `DirectWriteToPLC`(700) → `plcSocket.Send`(781) | FenetDriver.cs |

- 소켓은 **static 1개**(FenetDriver.cs:29), 생성자에서 즉시 접속, 전 송수신 lock 직렬화. 프레임당 `Sleep(20)`+동기 ACK 수신 → 최소 40ms/프레임.
- 읽기는 별개: `DoScan → RefreshMonitorMemory → mdReceive`로 블록을 캐시(FenetMemory)에 채우고, `Read(Observable)`(2240)는 캐시에서만 읽음(PLC 왕복 없음).

## 2. 질문 5: DLL의 계산법 vs PPT 계산법

| 항목 | DLL 소스(근거) | PPT/현행 확정 규칙 | 판정 |
|---|---|---|---|
| 디바이스 치환 | B→`'M'`, W→`'D'`, R→`'R'` (mdSend 628~639, enum FenetMemory.cs:19) | 동일 (B→M, W→D, R→R) | ✅ 일치 |
| B/W 주소 16진 | `ConnectionInfo["ADDRESS_NO", 0, 16]` (2085 등 전 지점) | 16진 | ✅ 일치 |
| 워드→바이트 ×2 | `strMemAddress = (deviceAddress * 2)` (724) → `%MB/%DB/%RB`+10진 바이트주소 | `%DB=워드×2`, `%RB=워드×2` | ✅ 일치 |
| 비트 주소 | `%MX`+비트주소 10진 (mdDevSet 560) / 워드=비트÷16 (1583) | `%MX=워드×16+비트` | ✅ 일치 |
| String 직렬화 | LENGTH=워드수, 1워드=ASCII 2자, 첫 자=하위바이트 (WriteWordA 1831~1871) | 화물번호 4자=2워드 | ✅ 일치 |
| **R 주소 진법** | **R도 16진 파싱** — String 쓰기/읽기 전 지점이 `[..., 16]` (2168/2180/2310) | **10진** (실 PLC 확정 2026-07-28, 현행 래더 조사(첨부)도 10진 연속 블록) | ⚠ **불일치** |

### ⚠ R 진법 불일치 상세 (질문 5의 "틀린 부분" 핵심)
- DB 실측값: `CONVEYOR:3=0020, :10=0090, :11=0100, :15=0140` — **10진으로 읽어야 호기당 10워드 연속 블록**(=(호기-1)×10). 16진으로 읽으면 0090→144, 0100→256으로 블록 간격이 불규칙해짐.
- 구 DLL은 이 값을 16진 파싱하므로 C/V#11 트래킹을 %RW256(%RB512)로 접근한다. **현행 마스터 PLC(실기동 검증 + 첨부 조사 모두)는 10진 워드(%RW100, %RB200)가 정답.**
- 신 WCS(EQP_TASK)는 10진으로 구현되어 실 PLC와 일치. → **구 ECS를 현행 PLC에 붙일 경우 R영역만은 소스가 틀린다**(구 시절 정합 여부는 당시 래더/운영 DB를 알 수 없어 판단 보류).
- 참고: 기존 V1.1 PPT(0709)의 R 주석(`R0102~R0103 %RB516~%RB518` 등)은 16진 계산 시절 값이 남은 것 — **V1.3에서 10진(%RB204~206)으로 정정 필요.**

### 기타 소스 특기사항(실사용 범위에선 무해하나 기록)
- 비트 세트/리셋 프레임은 디바이스 타입 인자를 무시하고 **%MX 고정**(560) — B(→M)만 쓰므로 무해.
- DATACOUNT를 10진 문자열 2자리 분해로 인코딩(746~749) — 100바이트 미만에서만 우연히 올바름(실사용 최대 4바이트라 무해).
- X/Y/SB/SW/WW/WR 타입은 mdSend/mdReceive에서 **아무것도 안 보내고 성공(0) 반환**(650).
- `IsSuccess`가 항상 true(235) — 전송 실패도 상위엔 성공으로 보임.

## 3. 질문 6: 첨부(260818, SC_2~5) 전수 대조 결과

첨부의 **M/D/R 토큰 71건 전부**를 구표기→실주소 변환 후 TB_OBSERVABLE(observables.tsv, DB 실측)과 역조회: **매핑 실패 0건** — 주소 존재성·소유 설비(CONVEYOR:3~10, VEHICLE:11~15) 100% 일치. **기존 메모리맵과 맞다.** (알람 슬라이드 SC#1~5는 완전 무결.)

단, **의미(핸드셰이크 짝·트래킹 순서) 차원에서 전사 오류 12+α건**을 발견 — 판정 근거는 ① 검증 완료된 V1.1 C/V#11·C/V#2 시나리오(이벤트+k↔ACK+k 정렬) ② 레거시 코드 `Conveyor.cs:984~1008`(이름 그대로 짝: LOAD_COMPLETE_01→LOAD_COMPLETE_ACK_01) ③ TB_LOCATION의 `CONVEYOR:nR/nS` 포트(R=RGV측이 **위치1**=FLAG_01·R베이스) ④ FRM_SCENARIO_TEST 검증 스텝.

### 3-4. 방향 체크 M0249/M0189 (8회 반복): 구 문서 복붙 잔재

- `M0249`·`M0189`는 구 V1.1 C/V#2 슬라이드의 "M024.9 / M018.9" 복붙(점만 탈락). 실주소로는 각각 CONVEYOR:5/CONVEYOR:2의 UNLOAD_REQUEST_ACK_02 — **방향과 무관.**
- 실제 방향 확인은 C/V별 DIRECTION_MODE **D워드**: C/V#n → `D030(n-1)` → `%DW(479+n)`. 예: C/V#3=D0302(%DW482/%DB964), C/V#4=D0303(%DW483/%DB966) … C/V#10=D0309(%DW489/%DB978).
- 값 의미도 구문서 기준 "입고 0 / 출고 1"(워드값)이지 "입고 ON/출고 OFF"(비트)가 아님.
- 통로 C/V#3~10은 방향 고정 라인(출고전용/입고전용)이라 시나리오상 방향 전환 자체가 없음 — 입출고 겸용은 C/V#2·#11뿐.

## 4. 결론

1. 첨부(PLC담당자 조사본)는 **주소 체계·메모리맵 차원에서 기존과 일치** — V1.3 시나리오의 근거로 사용 가능.
2. 단 §3-1~3-5의 전사 오류를 정정해 반영한다(정정표 §3-6).
3. 구 ECP DLL 계산법은 R 진법(16진)만 현행 확정 규칙(10진)과 다르고 나머지는 전부 일치 — 신 WCS 구현(10진)이 실 PLC와 정합하므로 현행 기준은 10진 유지.
