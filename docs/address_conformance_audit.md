# PLC 영역 정합성 감사 결과

| 항목 | 내용 |
|---|---|
| 문서 | LGLS WCS Renewal — PLC 주소 영역 ↔ 전 시스템 정합성 감사 |
| 일자 | 2026-08-20 |
| 방법 | 결정적 전수 대조(스크립트) + 다중 관점 조사 61개 에이전트(반증 검증 포함) |
| 기준 | PPT `Master PLC Memory Map` 슬라이드(58~67) · `PlcAddressMap.xml` · 구 ECS `observables.tsv` |

## 1. 결론

**영역(주소)은 맞다.** 블록 골격은 전수 일치하고, 사용자 엑셀 6시트 1,845셀도 불일치 0건이다.
**다만 "전 시스템이 그에 맞게 구성되어 있는가"는 아직 아니다.** 값은 맞는데 **경로**가 어긋난 곳이 있다.

| 구분 | 판정 |
|---|---|
| 블록 origin / stride (14개 블록) | ✅ 14/14 일치 |
| Signal 오프셋 (67개) | ✅ 66/67 일치 (예외 1건 = RGV To3) |
| 사용자 엑셀 6시트 주소 1,845셀 | ✅ 불일치 0 |
| 설비 대수 (C/V 15 · S/C 5 · RGV 1) | ✅ PPT·XML·코드 일치 |
| 시스템 경계 (IO_TASK · HOST_TASK · C++ Client) | ✅ DB 경유, PLC 주소 없음 |
| 실행 설정 | ⚠ 시뮬레이터 상태 |
| 단일 정의 원칙 | ⚠ 실제로는 정의가 2개 (XML · observables.tsv) |

## 2. 영역 대조 (질문 1)

### 2-1. 일치 확인된 골격

| 설비 | Event | Ack | Status/방향 | Command | Tracking |
|---|---|---|---|---|---|
| C/V | 256 / stride 32 | 1280 / 16 | D480 / 1 | — | (N-1)×10, 슬롯당 2워드 |
| S/C | 768 / 32 | 1536 / 16 | D256 / 16 | D768 / 16 | R0300 / 2 |
| RGV | 928 | 1616 | D336 | D848 | R0310 |

Signal 오프셋도 전부 일치 — C/V Event(+1 UC1 +2 LC1 +3 UC2 +4 LC2 +6 WO +9 UR2Ack), Ack(+1~+5),
S/C·RGV Status(+0 상태 +1/+2 알람코드 +3~+5 완료위치 +6~+8 현재위치 +9 운전모드),
Command(From 3워드 +0 / To 3워드 +3 / JobNo 2워드 +6).

### 2-2. 어긋난 2건

#### ① RGV Command `To3` — 다른 설비 영역 침범 (심각)

| | 값 |
|---|---|
| PLC 메모리맵 | `%DW853` (848 + 5, 연속) |
| 현행 XML | `%DW837` (`offset="-11"`) |
| 문제 | 837 = S/C #5 Command + 5 = **S/C #5 의 To(5,6)** 과 동일 워드 |

RGV 와 S/C #5 에 동시에 반송지시가 나가면 목적지 세 번째 워드(단)가 서로 덮어써진다.
XML 주석은 "구 ECS 원본이 비연속이므로 그대로 맞춘다"고 적었으나, 그 원본(`observables.tsv:372` `VEHICLE:1 TO_03=W0345`)은
`:522` `VEHICLE:15(S/C#5) TO_03=W0345` 와 **문자열까지 동일**하고, 같은 RGV 블록의 다른 태그는
`FROM=W0350/0351/0352`, `TO_01=W0353`, `TO_02=W0354`, `PALLET_ID=W0356` 으로 전부 연속이다.
`W0355`(=853) 자리만 비어 있다 — **구 ECS 설정의 복사 오류**로 보인다.

> 주의 : 이 값을 853 으로 바꿨다가 반자동 체인이 `JOB_STATUS=20` 에서 정체한 이력이 있어 현재 837 로 되돌린 상태다.
> 시뮬레이터도 같은 tsv 를 쓰므로 **시뮬레이터로는 판별할 수 없다.** 실 PLC 래더 확인이 유일한 판정 수단이다.

#### ② C/V #15 PalletExist 슬롯 순서 — 비선형

| 슬롯 | PLC 메모리맵 | XML/코드 전제 |
|---|---|---|
| +0 `%MX720` | #31 | 트랙 130 |
| +1 `%MX721` | #32 | 트랙 131 |
| +2 `%MX722` | #30 | 트랙 132 |

C/V #14 는 #27/#28/#29 로 선형인데 #15 만 **#31 → #32 → #30** 이다.
XML `<Equip plc="15" frTrack="130" toTrack="132">` 과 `CvThread.cs:3535 nCvNo = m_nFrTrackNo + s` 는 선형을 전제한다.

이 어긋남이 지금까지 드러나지 않은 이유가 소스에 명시돼 있다 — `ConveyorSim.cs:86-91` 주석 :

> "WCS 모드=트랙 순서 … EQP_TASK 가 슬롯 s 를 트랙 FR+s 로 해석하므로,
>  3트랙 C/V#15(PortOrder 3/1/2)도 트랙 130/131/132 와 정렬되게 한다"

즉 **시뮬레이터를 선형 전제에 맞춰 일부러 비틀어 두었다.** 로직2 실기동 통과는 실 PLC 대사가 아니다.
(`WorldModel.cs:123` 이 `CONVEYOR:15 Orders={3,1,2}` 로 비선형을 보존하고 있다.)

## 3. R(트래킹) 진법 — 아무도 확정하지 않은 항목

가장 파장이 큰 미결 항목이다. **벤더가 답을 준 적이 없다.**

| 문서 | R0300(S/C#1) 표기 | 해석 |
|---|---|---|
| V1.1 (2026-07-09) | `%RB1536` | 16진 (0x300=768 ×2) |
| V1.2 이후 (2026-07-28~) | `%RB600` | 10진 (300 ×2) |
| 현행 코드 기본값 | `%RB1536` | 16진 |

**두 표기 모두 우리가 쓴 것이다.** 벤더 원본 표는 `R0300` 같은 **문서표기만** 제공하고,
`%RB` 환산은 우리가 붙였다. V1.1 의 16진 근거는 벤더 사양이 아니라 구 ECS 소스(`FenetDriver.cs mdSend/mdReceive`)를
역분석한 결과이고, V1.2 의 10진은 그것을 우리가 "정정"한 것이다.

정리하면 :

- **16진** = 구 ECS 가 **실제로 전선에 내보내던 값** (현장 PLC 가 그 값으로 돌아갔다면 이쪽이 맞다)
- **10진** = 문서표기를 곧이곧대로 읽은 값

현재 배포는 `R_ADDR_MODE=HEX` 다. 그리고 **EQP_SIM 은 이 스위치를 따라가지 못하고 16진 고정**이라
(`cPlcAddrMap.RTrackWordFn` 훅이 `SYS_MAIN.cs:159` 한 곳에서만 주입됨), 지금까지의 실기동 검증은
EQP_TASK 와 EQP_SIM 이 **같은 가정을 공유한 순환 검증**이었다. 진법에 대해서는 아무것도 입증하지 못한다.

> **조치** : 실 PLC 에서 C/V #11 의 JOB NO 를 한 번 읽어 `%RB200` 인지 `%RB512` 인지 확인.
> 이 한 번의 확인으로 결정된다. DEC 로 정할 경우 EQP_SIM 도 함께 고쳐야 한다(현재는 반쪽 스위치).

## 4. 시스템별 구성 적합성 (질문 2)

| 시스템 | PLC 주소 취급 | 판정 |
|---|---|---|
| **IO_TASK** | 없음 — `_OD` 명령컬럼 + `OD_RQ_YN` 핸드셰이크, `_RD` 리드백만 | ✅ 설계대로 |
| **HOST_TASK** | 없음 — `CV_DATA`/`SC_DATA_LGLS` 읽기 + 보고 플래그 | ✅ 설계대로 |
| **C++ Client (Ecs)** | PLC 소켓 없음. 상태창 라벨에 번지 표시용 조회만 | ✅ 경계 지킴 |
| **EQP_TASK** | XML 1순위 · tsv 폴백 | ⚠ 아래 참조 |
| **EQP_SIM** | **tsv 단독** (XML 은 시나리오 테스트 창에서만) | ⚠ 출처 2개 |
| **C# Ecs (WCS/CSharp)** | 자체 MELSEC 드라이버 + 자체 D주소 | ❌ 경계 파괴 |

### 4-1. EQP_TASK — "XML 하나만 고치면 된다"는 절반만 성립

| 따라가는 것 | 따라가지 않는 것 |
|---|---|
| C/V 블록 base 4종 (Event/Ack/Direction/Tracking) | **개별 Signal 오프셋** — `CvThread.cs:3080~3084` 등에 `+1/+2/+3/+4/+6/+9` 리터럴 |
| S/C·RGV 통신주소 전량 (`TagTable`) | 슬롯 stride(포지션당 워드수) |
| 알람 4비트 (`GlobalBit`) | `<Equipments>` 15행 — 아무도 읽지 않는 죽은 정의 (트랙 매핑은 `WCS_DB.INI` COMM 섹션) |
| 메모리맵 화면 · 시나리오 테스트 창 | 메모리맵 화면의 `[CV 데이터 쓰기]` 버튼 (주소 직접 계산) |

즉 XML 의 `<Signal offset>` 을 고쳐도 **자동운전 통신은 바뀌지 않는다.** 값이 현재 일치하므로 지금은 무해하지만,
"XML 이 단일 진실원" 이라는 전제로 XML 만 고치면 조용히 어긋난다.

### 4-2. 관측 공백 2건

| 항목 | 내용 |
|---|---|
| **ERR_CODE_RD 미정의** | S/C 5대의 에러코드 관측 태그가 XML 에 없다. XML 단일화 이후 `ERR_CODE_RD` 가 항상 `'0000'` 으로 기록되어 **이중입고(54)·공출고(58) 가 WCS 로 올라오지 않는다.** (tsv 에는 `W010A~014A` 로 있었다 = Status +10 자리) |
| **S/C #2~#5 · RGV 알람 미관측** | 알람 주소가 `<Global>` 단일 상수(786/787/1539/1540)로 정의돼 있고, 이 값은 실제로 **S/C #1 전용 비트**다. `CvThread` 주석은 "CV 전 공통"이라고 잘못 설명한다. |

### 4-3. C# Ecs 클라이언트 — 경계 파괴 (별건)

`WCS/CSharp/Ecs` 가 **자체 MELSEC 3E 드라이버**(`InterfaceSk.cs:54 MelsecEthernetSk`)와
**자체 D레지스터 상수**(`D_TRACK_BASE=1000`, `D_SC_STATUS_BASE=2000`, `D_SC_CMD_BASE=2100`,
`D_RTV_STATUS_BASE=3000`)를 들고 있고, `Ecs.csproj` 에 정식 컴파일된다.

이 주소들은 **PLC 메모리맵에도 XML 에도 없는 값**이고, 실 PLC 는 LS XGT FEnet 인데 프로토콜은 미쓰비시다.
`EcsConfig.xml` 에 설비 노드가 없어 전부 `127.0.0.1:5000/5001/5002` 로 접속 시도한다.
또 `ManualScDialog` 의 수동 크레인 명령은 DB 에도 PLC 에도 쓰지 않고 **성공 메시지만 표시**한다.

> 이 프로젝트는 C++ Client 의 C# 이식 진행분으로 보인다. 현장 배포 대상이 아니라면 무해하나,
> 배포 경로에 들어가면 잘못된 주소로 실 PLC 에 쓰기를 시도할 수 있다.

## 6. 우선순위

| 순위 | 항목 | 왜 |
|---|---|---|
| **1** | R 진법 확정 (3장) | 트래킹 전 영역의 위치가 갈린다. 실 PLC 1회 확인으로 결정 |
| **2** | RGV `To3` 확정 (2-2 ①) | S/C #5 반송지시 파괴 가능. 실 래더 확인 필요 |
| **3** | C/V #15 슬롯 순서 (2-2 ②) | 로직2 입고가 실 PLC 에서 어긋날 수 있다. 시뮬레이터로는 검증 불가 |
| **4** | `ERR_CODE_RD` 복원 | 이중입고·공출고가 현재 검출되지 않는다 |
| **5** | S/C #2~#5 · RGV 알람 관측 | 설비 알람이 올라오지 않는다 |
| 6 | `CvThread` 오프셋 하드코딩 정리 | 지금은 값이 같아 무해. XML 단일화 완성용 |
| 7 | C# Ecs 배포 경로 격리 | 잘못된 주소·프로토콜 |

1~3 은 **실 PLC 확인 없이는 결론 낼 수 없다.** 시뮬레이터는 세 건 모두 같은 가정을 공유하므로 판별력이 없다.
